02 Why the driver keeps breaking

Every outage on this bench so far traces to one design fact: Ubuntu ships the NVIDIA kernel module two different ways, and only one of them survives a kernel upgrade.

Two delivery paths

  • Prebuilt — linux-modules-nvidia-595-open-6.8.0-136-generic. A compiled .ko shipped for one exact kernel. No compiler needed. Silently useless the moment you boot a different kernel.
  • DKMS — nvidia-dkms-595-open. Source that rebuilds itself for whatever kernel you boot. Survives upgrades, but needs a working compiler at install time.

A node is healthy when at least one path lands a module in the kernel it actually booted. Both failures on this bench were a node where neither did.

The compiler rule

Kernel 6.8.0 on Ubuntu 22.04 is built with gcc-12, and its build flags include -ftrivial-auto-var-init=zero, which gcc-11 does not recognize. If gcc-12 is absent, every DKMS build fails with cc: error: unrecognized command-line option. Presence of gcc-12 predicted GPU health on all seven nodes with no exceptions.

Note that the default gcc does not need to be 12. Nodes 01, 02 and 04 default to gcc-11 and build fine, because DKMS selects the kernel's compiler when it is installed. What matters is that /usr/bin/gcc-12 exists.

03 Health check

Two levels: one node in full detail, or all seven at a glance. Both are read-only and need no sudo.

One node — gputool device

The single command to run on an unfamiliar machine, or first when a GPU job fails for no obvious reason. It reports host, GPU, driver health, storage, Conda and gputool itself on one screen, and closes with a verdict. 

gputool device            # full local report
gputool device --online   # also check GitHub for a newer gputool

The Driver health block is the part worth reading even when the GPU looks fine — it is the only place the four conditions that predict surviving the next kernel upgrade are shown together: 

Driver health
   ● Kernel module      : 4 loaded
   ● DKMS               : nvidia/595.84, 6.8.0-136-generic, x86_64: installed
   ● Build toolchain    : gcc-12 present (kernel was built with it)
   ○ nvcc toolkit       : 13.0

A node that shows DKMS: no NVIDIA module registered or Build toolchain: gcc-12 MISSING is working today and will lose its driver on the next kernel upgrade. On WSL2 the module and DKMS rows read n/a — the driver comes from the Windows host, so there is nothing to check on the Linux side.

All seven — one line each

      "$(dkms status 2>/dev/null | grep -ci nvidia)"'
done

Healthy output has smi=OK, gcc12=yes, and dkms of 1 or more on every line.

Windows caveat

If you pipe a script from a Windows checkout of edgeAI into ssh, strip carriage returns first — tr -d '\r' < script.sh | ssh host 'bash -s'. The repo stores LF, but core.autocrlf=true hands you CRLF in the working tree, and bash answers with syntax error near $'{\r'.

04 Repair ladder

Work top to bottom and stop at the first rung that restores nvidia-smi. All three run as cmpeadmin. Only the third requires a reboot or destroys state.

Rung 1 Module present but not loaded
Test: modinfo nvidia prints a version  ·  lsmod | grep nvidia is empty

Nothing is missing. The module just was not inserted — usually because the driver landed after the last boot. This was node 07. Seconds to fix, no reboot.

sudo modprobe nvidia nvidia-uvm nvidia-modeset
nvidia-smi
Rung 2 Module missing for the running kernel
Test: modinfo nvidia says not found  ·  dkms status is empty

The DKMS package was removed, or the prebuilt module targets a kernel you are not running. Install the compiler first — without it the DKMS trigger fails mid-install and leaves dpkg half-configured.

# 1. compiler must exist before any DKMS build is triggered
sudo apt install -y gcc-12

# 2. reinstall both delivery paths together
sudo apt install -y nvidia-driver-595-open nvidia-dkms-595-open

# 3. confirm a module now exists for the running kernel
dkms status
modinfo nvidia | head -2

sudo reboot
Rung 3 Mixed driver branches / dpkg wedged
Test: dpkg -l | grep nvidia shows iF or two driver branches (580 and 595)

This is node 05's case. Partial removals had left 580 and 595 packages interleaved and two packages half-configured. Nothing short of a clean sweep resolves it. Destructive — removes all NVIDIA packages and reboots.

# purge every NVIDIA package and its residue
sudo apt-get purge -y "*nvidia*"
sudo apt-get autoremove --purge -y
sudo rm -rf /var/lib/dkms/nvidia* /usr/src/nvidia-*
sudo rm -f  /lib/modules/*/updates/dkms/nvidia*.ko
sudo rm -rf /lib/modules/*/kernel/nvidia-*/

# rebuild the toolchain the kernel expects
sudo apt update
sudo apt install -y build-essential dkms linux-headers-$(uname -r) gcc-12 g++-12
sudo update-alternatives --install /usr/bin/gcc gcc /usr/bin/gcc-12 100
sudo update-alternatives --install /usr/bin/g++ g++ /usr/bin/g++-12 100

# clear any half-configured state, then reinstall
sudo apt-get --fix-broken install -y
sudo dpkg --configure -a
sudo update-initramfs -u
sudo apt install -y nvidia-driver-595-open nvidia-dkms-595-open

sudo reboot
If a DKMS build still fails after gcc-12 is installed

Force the compiler explicitly and rebuild for the running kernel only:

sudo dkms remove nvidia/595.84 --all
sudo CC=/usr/bin/gcc-12 dkms install nvidia/595.84 -k $(uname -r)

Read the real error at /var/lib/dkms/nvidia/<ver>/build/make.log — it is world-readable, so you can inspect it from the student account before escalating. A stale /var/crash/nvidia-dkms-*.crash file will also mask errors with Cannot create report: File exists; delete it.

06 gputool

Per-user helper at ~/.local/bin/gputool, installed from the repo. It carries the device report and the hf-cache commands in section 07. No sudo, so it can be reinstalled by the student account at any time. 

curl -fsSL https://raw.githubusercontent.com/lkk688/edgeAI/main/jetson/install_gputool.sh | bash
source ~/.bashrc

The installer backs up any existing copy to gputool.bak before replacing it.

All seven nodes carry the same build, with device, hf-cache, serve-vllm and serve-llamacpp --mtp.

Why setup-llamacpp now avoids the conda toolchain

It used to configure and build through conda run, which puts conda's gcc 11.2 at the front of PATH. That works on Ubuntu 22.04 and fails on 24.04 with undefined reference to __libc_csu_fini — a glibc symbol removed in 2.34, newer than the compiler conda ships. The 4090 box runs 24.04, so llama.cpp would not build there at all; the seven 22.04 nodes were fine, which is exactly why the bug went unnoticed.

Four things changed:

  • System compilers, by absolute path. Picks the newest matched gcc-N/g++-N pair and passes it as CMAKE_C/CXX_COMPILER and CMAKE_CUDA_HOST_COMPILER. A matched pair matters: that machine has gcc-12 but no g++-12.
  • System cmake preferred, falling back to the conda env's copy called by absolute path, so conda's compilers never lead PATH. Ninja is resolved the same way and passed as CMAKE_MAKE_PROGRAM.
  • Build only this GPU's architecture, from compute_cap — sm_89 on the 4090, sm_120 on the bench.
  • Errors are shown. The build is teed to build/gputool-build.log and the first real compiler errors are printed on failure. The old code checked $? after a pipe, which reports tee's status — so a failed build could read as a successful one.

Verified by wiping the build directory on the 24.04 machine and rebuilding: it selected /usr/bin/cmake, /usr/bin/gcc-13, sm_89, -j30, and finished with the CUDA backend active and zero references to conda-linux-gnu.

Chat and agent come from a pip package

The terminal chat client and the ReAct agent sidecar used to be delivered by fetching a single chat.py from GitHub and by pointing at a repo checkout. Agent mode therefore needed the whole edgeAI tree, and the sidecar looked for /Developer/edgeAI/… — a path that exists only on the Jetson images, so on a desktop the lookup silently failed and the feature quietly went missing.

They are now one installable package, gputool-ai:

gputool install-ai            # all extras (chat + agent)
gputool install-ai base       # chat only, no FastAPI stack

# or directly, on any node, with no repo checkout:
pip install "gputool-ai[all] @ git+https://github.com/lkk688/edgeAI@main#subdirectory=packages/gputool-ai"

It installs two console scripts, gputool-chat and gputool-agent, and pulls edge-agent in automatically as a dependency. gputool chat and gputool agent prefer them when present and fall back to the old single-file download, so nodes that have not installed the package keep working.

No absolute paths

Everything resolves in the same order, and never reaches outside the user's control:

  1. an environment variable — GPUTOOL_WORKSPACE, GPUTOOL_ENV_FILE, GPUTOOL_DIR
  2. the current working directory — so cd myproject && gputool agent start acts on that project
  3. ~, for the shared ~/.env.local key file

AGENT_WORKSPACE is still honoured so existing sidecar deployments keep working. Verified on a node: with GPUTOOL_WORKSPACE=/tmp/wsdemo, the sidecar's /health reports "default_root":"/tmp/wsdemo".

Model choice, and asking for the right thing

A 4B model on the bench and a hosted model are good at different things, and the prompt should say so. Picking a provider therefore also picks a command style, either of which can still be overridden.

The simple style is written for a Linux class: one short command per step, no multi-line scripts or heredocs, prefer the ordinary utilities a student should learn, and explain in one sentence what the command did. That is both what a 4B model does reliably and what a student should be reading. Asked how much disk is free, the agent answers with df -h and nothing else — not a three-line awk pipeline.

A hosted provider with no key set is reported plainly (minimax … NO KEY (set MINIMAX_API_KEY)) rather than failing later with a 401.

Memory: plain Markdown on disk

Every session is written to ~/.gputool/memory as it runs — incrementally, so a crash or a timeout still leaves a usable record, which is exactly when you want one. Markdown rather than a database: a student can open it, a grader can diff it, grep finds things, and it survives the tool being uninstalled. 

memory/
  INDEX.md                     one row per session
  commands.md                  every command ever run, with exit status
  sessions/2026-08-29-44f2.md  task, each step's thought + command + output, answer

commands.md is the file students will actually use — a searchable history of what worked on this machine: grep -n 'tar' ~/.gputool/memory/commands.md.

Memory that changes behaviour, not just an archive

Successful commands from earlier sessions are fed back into the system prompt, so the agent reuses what already worked here instead of rediscovering it. After two sessions the store held df -h and du -sh /var/* | sort -hr | head -3, and both were offered to the next run. It is the cheapest form of long-term memory that actually affects what the model does.

Testing the agent end to end

gputool agent test exercises every agent tool against a real model and returns a non-zero exit status on any failure, so it drops straight into CI. It deliberately does not mock the model: each scenario runs in a fresh scratch workspace and is judged by inspecting the filesystem afterwards, not by reading the model's answer — an agent that claims to have written a file but did not still fails. 

gputool vllm start Qwen/Qwen3.5-4B 8000     # 1. a model
gputool agent start                          # 2. the sidecar
gputool agent test --base-url http://127.0.0.1:8000/v1 --model Qwen/Qwen3.5-4B
agent    : http://127.0.0.1:8002  tools=read_file,grep,search_files,write_file,edit_file
model    : Qwen/Qwen3.5-4B via http://127.0.0.1:8000/v1
  [PASS] read_file        1.7s  steps=1  tools=read_file             found the token in the answer
  [PASS] grep             3.8s  steps=2  tools=grep,read_file        located the TODO
  [PASS] search_files     1.8s  steps=1  tools=grep                  found the helper
  [PASS] write_file       4.2s  steps=3  tools=search_files,read_file,write_file  OUTPUT.md written
  [PASS] edit_file        4.4s  steps=2  tools=read_file,edit_file   guard added to divide()

--repeat N takes the median over N runs for timing work, --only NAME isolates one scenario, and --keep leaves the scratch workspace behind so you can see what the agent actually did. Because --base-url and --model are plain flags, the same suite benchmarks any OpenAI-compatible endpoint — a local llama.cpp server, vLLM, or a hosted API — which makes it a reasonable harness for comparing models on tool use rather than on prose.

What the tools column is telling you

Note the search_files row: the task was satisfied, but the agent reached for grep rather than search_files. The scenario passes because the outcome was correct, and the tools column is what surfaces the divergence. When you change the tool descriptions or the ReAct prompt, that column is the signal to watch — a tool the model never selects is either badly described or redundant.

Giving the agent a terminal

File tools alone cannot build, test, or install anything, so the agent has a run_terminal tool modelled on how Claude Code and Codex expose a shell: working directory persists between calls, output is capped from both ends (a 50k-line build log is useless but its head and tail are exactly what matters), timeouts return partial output rather than nothing, and the exit code is always reported so the model can tell "ran and failed" from "did not run".

The bench nodes have no Docker and installing it needs root, so there the agent runs on the host — but package installs still must not leak. On first use the host backend builds itself a uv virtualenv at ~/.gputool/agent-venv (override with GPUTOOL_AGENT_VENV) and puts it at the front of PATH. It is seeded with pip and created with --system-site-packages, so heavy things already present — torch, CUDA bindings — stay visible without being copied, while anything the agent installs lands only in its own environment. uv itself is pip-installed beside the sidecar's interpreter if missing; no privileges needed.

Verified on a node:

which python pip
  ~/.gputool/agent-venv/bin/python
  ~/.gputool/agent-venv/bin/pip

pip install cowsay   →  ~/.gputool/agent-venv/lib/python3.12/site-packages/cowsay/
conda env            →  ModuleNotFoundError: No module named 'cowsay'
The agent never runs privileged commands

sudo, su, pkexec, doas and runuser are refused before execution — anywhere in the command, including after ; or && and inside $(…). sudoku and pip install sudoku are not affected.

The refusal tells the model what to do instead, so it reports back rather than hunting for a workaround:

REFUSED: this command needs elevated privileges, and the agent does not run them.
If a system package is genuinely required, name it in your final answer and a
human will install it. For Python packages, use the agent's own environment:
  uv pip install <package>        (or: pip install <package>)

Asked to run sudo apt-get install -y cowsay, the agent stopped and answered: "I cannot run it as it requires elevated privileges. You should install it yourself by running: sudo apt-get install -y cowsay" — which is the behaviour you want on a shared teaching cluster. This is a policy guard, not a security boundary: the host backend has your user's filesystem access, and only the Docker backend actually confines it.

One fix worth copying if you build your own

The agent's first shell task failed with pytest: command not found, then pip: command not found, then sudo: a password is required — it burned every step rediscovering that its shell had nothing in it. bash -lc inherits the PATH the service started with, and on these nodes conda goes on PATH late in .bashrc, after the guard that returns early for non-interactive shells. The host backend now prepends the directory of the interpreter actually running the sidecar, which is the environment the operator meant the agent to use. After the fix the same task installed pytest and reported the result in three steps.

07 Shared model cache

All seven nodes can mount one 364 GB HuggingFace cache hosted on the lab's RTX 4090 box, so a model downloaded once is available everywhere. No sudo is involved anywhere in the chain. 

  cmpe28801..07              lkk-intel13 (RTX 4090)
  10.31.96.x                 10.31.81.235
  ┌──────────────┐           ┌────────────────────────┐
  │ ~/hf-shared  │◀──SFTP───▶│ /DATA10T/huggingface   │
  │ (rclone FUSE)│  ~11 MB/s │ 364 GB · 56 repos      │
  │              │           │ 4.5 TB free of 9.1 TB  │
  │ ~/.cache/    │           └────────────────────────┘
  │  rclone 20G  │  ← hot blobs served locally at 1.4 GB/s
  └──────────────┘

The transport is rclone over SFTP mounted with FUSE. It works unprivileged because /dev/fuse is world-accessible on these hosts and fusermount3 is installed; rclone itself is a single static binary in ~/.local/bin.

Using it

gputool hf-cache setup     # once per node: rclone, SSH key, remote config
gputool hf-cache mount     # attach at ~/hf-shared
gputool hf-cache status    # remote, mount, local cache size, HF_HOME

# Opt in for one shell only:
export HF_HOME=~/hf-shared

# ...or for every shell, including batch jobs:
gputool hf-cache enable
gputool hf-cache disable   # undo; 'unmount' detaches the mount

Nothing changes until you run enable. All seven nodes are currently set up but not enabled, so jobs still use each node's local cache by default.

Why enable writes to the top of .bashrc

Ubuntu's stock .bashrc returns at line 8 when the shell is not interactive — and a batch job arrives as ssh node 'python train.py', which is exactly that case. A block appended at the end never runs for the workload that matters, so enable prepends above that guard instead. The auto-mount it installs takes a lock directory so parallel logins cannot race.

What to expect

PathThroughputMeaning
Warm read, local VFS cache1.4 GB/sSecond and later reads of a blob
Raw ssh between the subnets11.7 MB/sThe hard ceiling — a ~100 Mbit link
Cold read over the mount11.0 MB/srclone adds almost no overhead
From WSL on the Windows box11.4 MB/sSame ceiling campus-wide
Direct from the HuggingFace CDN5.9 MB/sWhat you avoid by sharing

So the shared cache is roughly twice as fast as re-downloading, and costs no local disk for the store itself. It is not, however, local-disk fast on first touch: a 14 GB model takes about 20 minutes to stream in once, then loads instantly from the local VFS cache. Treat it as a fast mirror, not as local storage.

Two caveats worth knowing before you rely on it

New downloads through the mount lose deduplication. SFTP cannot create symlinks, so HuggingFace copies blobs into snapshots/ instead of linking them — roughly double the space on the shared volume for anything fetched this way. Content already on /DATA10T is unaffected and reads back normally, because rclone follows the server-side symlinks. To avoid the tax on a large model, download it directly on the 4090 box.

The store is shared with other people. /DATA10T/huggingface is world-writable and already has content from more than one account. Anything you download lands where others can see and delete it, and vice versa. Do not put anything gated or private there.

08 Serving a model

gputool can bring up an OpenAI-compatible endpoint two ways. They are not interchangeable — pick by what the GPU has to do.

UseCommandBest for
vLLMserve-vllmFull-precision weights, many concurrent requests — continuous batching keeps the GPU busy when a class hits one node at once
llama.cppserve-llamacppQuantized GGUF weights, one or two users, or a model that will not otherwise fit in 16 GB

vLLM

gputool setup-vllm                 # once per env; installs into py312 by default
gputool serve-vllm start           # Qwen/Qwen3.5-4B on port 8000
gputool serve-vllm status          # process, API, GPU memory, log location
gputool serve-vllm stop            # kills the server and sweeps stray workers

# A different model, port, or context window:
gputool serve-vllm start Qwen/Qwen3.5-9B 8001 --max-len 4096 --max-seqs 8

# Anything after -- is passed straight through to vLLM:
gputool serve-vllm start -- --enable-prefix-caching

Defaults are --max-len 8192, --gpu-mem 0.92 and --max-seqs 16. Those are measured, not guessed: they are the values at which Qwen3.5-4B actually comes up on a 16 GB RTX 5080. The engine then reports 

Available KV cache memory: 3.68 GiB
GPU KV cache size: 98,304 tokens
Maximum concurrency for 8,192 tokens per request: 12.00x

— so roughly a dozen students can hold a full-length conversation at once on one node.

Why the ceiling is lower than you would expect

Qwen/Qwen3.5-4B is multimodal (image-text-to-text, Qwen3_5ForConditionalGeneration), so the vision tower and the mm-encoder cache draw on the same 16 GB as the weights and KV cache. A first attempt at --max-len 16384 --gpu-mem 0.90 loaded the weights fine and then died in CUDA-graph profiling: 

torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 1.03 GiB.
GPU 0 has a total capacity of 15.47 GiB of which 1006.81 MiB is free

If you hit that, lower --max-seqs first — CUDA-graph memory scales with it and it costs the least — then --max-len. Raising --gpu-mem past about 0.92 does not help; it hands vLLM more of a budget the card does not have.

Pair it with the shared cache

Qwen/Qwen3.5-4B is already on /DATA10T, so mounting the shared cache first avoids re-downloading 8.8 GB from the internet on every node: 

gputool hf-cache mount
export HF_HOME=~/hf-shared
gputool serve-vllm start

vLLM reads HF_HOME like any other HuggingFace client, and serve-vllm start echoes the value it picked up so you can see which cache it is about to use.

Startup blocks until the log reports the API is live, then prints the endpoint. First run is slow — it is streaming weights — so the wait is generous; if it is still loading after 15 minutes the command hands back with a tail -f to watch. Stopping sweeps vLLM's worker processes as well as the parent, because a stray worker keeps the GPU allocated and the next start then fails on memory.

If the engine dies at startup

vLLM's flashinfer backend does not ship prebuilt attention kernels — it JIT-compiles them on first run, shelling out to ninja and nvcc. Neither is on the default PATH here: ninja installs into the conda env's bin, and the CUDA toolkit lives under /usr/local/cuda. Miss either and the engine dies with a bare FileNotFoundError: 'ninja' buried under a long traceback, after having already spent several minutes loading weights.

setup-vllm installs ninja, and serve-vllm puts both the env's bin and the CUDA toolkit on PATH before launching, warning up front if either is absent. If you run vllm serve by hand instead, export them yourself: 

export PATH="$HOME/miniconda3/envs/py312/bin:/usr/local/cuda/bin:$PATH"
export CUDA_HOME=/usr/local/cuda
Second start is much faster

Two caches make the difference. The rclone VFS cache keeps the weights local after the first read, and vLLM writes its compiled graphs to ~/.cache/vllm/torch_compile_cache. On these nodes that took a cold start of roughly 14 minutes down to well under a minute.

MTP — multi-token prediction

Unsloth's *-MTP-GGUF repos carry a multi-token-prediction head. The model drafts several tokens per step and verifies them in one pass, so decode gets faster without changing the weights. llama.cpp gained support for it in May 2026; the build gputool setup-llamacpp produces has it. 

gputool serve-llamacpp start Qwen3.5-4B-Q8_0.gguf 8080 --mtp
gputool serve-llamacpp start Qwen3.5-9B-Q8_0.gguf 8080 --mtp --spec-n 8

DFlash2 — and how far a 27B can be pushed

z-lab/Qwen3.8-27B-DFlash2-GGUF is not a model. It is a block-diffusion drafter that runs beside a target model, so the GGUF files are 1–4 GiB for a nominally 27B repo. The 3-bit quant fits, and is broken

A 27B does run on a 5080 at UD-Q3_K_XL — 15,541 MiB of 16,303, only 762 MiB spare, at up to 155 tok/s. It is also the faster of the two machines here, because 3-bit weights move less memory per token than the 4090's 4-bit copy. None of that matters, because the answers are wrong.

Given one identical question, the 4-bit copy answered correctly in 497 tokens and stopped. The 3-bit copy never produced an answer at all — it filled 800 tokens with circular reasoning_content and hit the length limit. Its reasoning was on-topic but never converged.

So the 5080 fleet cannot usefully run this 27B: the quant that fits destroys the reasoning, and the quant that reasons does not fit. Use the 4090 for 27B work, or stay at 4B–12B on the bench where Q8_0 and NVFP4 both hold up.

Reading the result

NVFP4 does not make a model faster — it makes a bigger model fit. A 12B model runs here at 85% of a 4B model's single-stream speed, in 1.5 GB more VRAM. Under eight concurrent requests the gap closes to 5%, because batching hides per-token cost. If answer quality matters more than raw throughput, that is a good trade.

The real price is KV cache tokens, not memory. Gemma is given more KV memory than Qwen (4.19 vs 3.56 GiB) yet holds 2.3× fewer tokens, because a 12B model has more layers and heads and each cached token costs proportionally more. That caps concurrency at 4.26× against Qwen's 10×. For a lab section where thirty students share one node, that ceiling will bite before tokens/sec does.

Output quality on an identical prompt

Asked to explain the gcc-12 DKMS failure from section 02 in two sentences:

This took a node off the network — read before serving a new model

A first load of an NVFP4 model made node 02 unreachable and it had to be power cycled. The cause was not GPU memory. FlashInfer JIT-compiles its kernels on first use and runs one compile job per core — 20 on these machines, at 1–2 GB each. With 30 GB of RAM and only 2 GB of swap, the box thrashed and the kernel OOM-killer took sshd.

The measured difference, same model, same node:

Even so, watch free -g during a first load of any new quantized model, and consider a watchdog that kills the server rather than letting the OOM-killer choose: 

( while sleep 5; do
    avail=$(free -m | awk '/^Mem:/{print $7}')
    [ "$avail" -lt 2500 ] && { pkill -9 -f "[v]llm.entrypoints"; break; }
  done ) &

Disk — watch 04

Note that du overstates what a cache purge will return: uv and conda hardlink cache files into environments, so deleting 62 GB of apparent cache on 04 returned 20 GB of real blocks. Trust df, not du, when planning space.

  • Driver drift on 03 and 04. They run 580.95.05 and 580.159.03 against 595.84 on the other five. Aligning all seven on 595.84 makes student builds reproducible across the bench.
  • Obsolete kernels retained. Several nodes still carry 6.8.0-124 headers and images. DKMS rebuilds for every installed kernel, so each stale one is another chance for a build to fail and wedge the install. sudo apt autoremove --purge clears them.
  • Duplicate apt source. Mozilla is registered in both mozilla.list and mozilla.sources, producing 24 warnings on every apt update. Harmless; delete /etc/apt/sources.list.d/mozilla.list to silence.
  • No Docker on any node. Worth knowing before assigning container-based work.

11 Keeping them healthy

Four invariants. Hold these and the failure mode above cannot recur.

  1. gcc-12 stays installed on every node. It is the single predictor of whether a driver survives a kernel upgrade. Install it during provisioning, never as a reaction.
  2. Prefer DKMS over prebuilt modules. nvidia-dkms-*-open rebuilds for any kernel; linux-modules-nvidia-* is pinned to one and fails silently after the next upgrade.
  3. Never leave two driver branches installed. Mixing 580 and 595 packages is what produced the wedged state on 01 and 05. Purge before switching branches.
  4. Cap compile and JIT parallelism on these nodes — 20 cores against 30 GB of RAM and 2 GB of swap is the ratio that took a node off the network. gputool now caps llama.cpp builds by free RAM and exports MAX_JOBS=4 for vLLM, but anything you run by hand needs the same restraint.
  5. Prefetch big models on the 4090 box, not through the mount — downloads written over SFTP lose HuggingFace's symlink deduplication and take roughly double the space on the shared volume.
  6. Run the health check after any kernel update — and before the first lab session of the week. A node whose module failed to rebuild looks completely normal until someone calls torch.cuda.is_available().
