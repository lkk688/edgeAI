Rebuilding a CMPE 288 Node

What to install after IT reimages a bench machine, in the order that matters. Every version below was read off node 01 as it stands now, not from documentation — and the ordering exists because getting it wrong has already cost this fleet three broken nodes and one power cycle.

00 What a fresh image looks like

Surveyed on 288-01 after the rebuild. A reimaged node arrives like this:

OSUbuntu 22.04.5 LTS, kernel 6.8.0-138-generic
GPUNVIDIA 10de:2c02 (RTX 5080) + Intel iGPU
NVIDIA driverabsent — nvidia-smi missing, 0 modules loaded
nouveau11 modules loaded — currently driving the card
Dockerabsent
gcc-12absent — the one that breaks DKMS
dkms / cmake / curlabsent
Kernel headerspresent for 6.8.0-138
Secure Bootdisabled — no MOK enrolment needed
Hardware20 cores, 30 GB RAM, 2 GB swap, 336 GB free
SSH keyswiped for every account, host keys regenerated

Everything below runs as cmpeadmin, which needs a password for sudo — so this is a console or interactive-SSH job, not something to automate over a batch connection.

01 The NVIDIA driver

Ubuntu's own recommendation and the fleet standard agree, which makes this easy: ubuntu-drivers devices on 288-01 marks nvidia-driver-595-open as recommended, and that is the 595.84 the other six nodes already run.

PackageVersion availableWhy
nvidia-driver-595-open595.84-0ubuntu0.22.04.1Ubuntu-recommended; matches nodes 02, 06, 07
nvidia-dkms-595-open595.84-0ubuntu0.22.04.1Rebuilds the module for any future kernel
gcc-1212.3.0-1ubuntu1~22.04.3Install first — see below
dkms2.8.7-2ubuntu2.2Pulled in anyway; listed for clarity

nvidia-driver-610-open is also offered. Do not take it: parity across the bench is worth more than a newer point release, and 595.84 is the version every other measurement in the runbook was taken on.

Install gcc-12 before the driver, not after

Kernel 6.8.0 is built with gcc-12, and its build flags include -ftrivial-auto-var-init=zero, which gcc-11 does not recognise. If gcc-12 is missing when the DKMS trigger fires, the module build fails, dpkg is left half-configured, and you get a machine whose nvidia-smi cannot reach a driver. That is exactly what happened to nodes 01, 05 and 07 — presence of gcc-12 predicted GPU health on all seven, with no exceptions.

The system default gcc does not need to be 12. Nodes 02 and 04 default to gcc-11 and build fine, because DKMS selects the kernel's compiler when it is installed. What matters is only that /usr/bin/gcc-12 exists.

1 · Toolchain first
sudo apt update
sudo apt install -y gcc-12 dkms build-essential curl cmake \
                    linux-headers-$(uname -r)
2 · Driver, both delivery paths

Ubuntu ships the module two ways and a node is healthy when either lands one in the kernel you booted. Installing both means a kernel upgrade cannot strand you. 

sudo apt install -y nvidia-driver-595-open nvidia-dkms-595-open \
                    linux-modules-nvidia-595-open-generic-hwe-22.04

This also blacklists nouveau, which is currently driving the card — that is why a reboot is required rather than optional.

3 · Confirm the build succeeded, then reboot
dkms status                 # expect: nvidia/595.84, 6.8.0-138-generic: installed
sudo reboot

Check dkms status before rebooting. If it is empty the build failed, and rebooting only turns a fixable error into a machine with no display driver.

4 · Verify after reboot
nvidia-smi                                  # RTX 5080, 595.84
lsmod | grep -c '^nvidia'                   # expect 4
lsmod | grep -c nouveau                     # expect 0

02 Docker and GPU containers

Worth doing while you have root. Docker's absence is the only reason Terminal-Bench and other container work run on the 4090 instead of the bench.

docker-ce is not reachable — no Docker repo is configured on the fresh image. docker.io 29.1.3 is in Ubuntu's universe and is the shorter path; use Docker's own repo only if you specifically need their build. 

sudo apt install -y docker.io
sudo systemctl enable --now docker
sudo usermod -aG docker $USER          # and the student account too:
sudo usermod -aG docker 010796032
# group change needs a fresh login to take effect

For --gpus all you also need the NVIDIA container toolkit, which is not in Ubuntu's repos — it needs NVIDIA's: 

curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt update && sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

Verify with a container that has to see the GPU:

docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi
nvidia-smi passing is not the test

Enumerating the device and running a kernel on it are different things, and the gap between them is where a Blackwell card bites. The widely-recommended pytorch:2.5.1-cuda12.4 image reports the RTX 5080 correctly and then fails on the first matmul: 

image arch list: sm_50 … sm_90
device:          sm_120
CUDA error: no kernel image is available for execution on the device

The cu12.4 images stop at sm_90; the 5080 is sm_120. Use a cu12.8 image, which carries sm_120 kernels. This one is verified computing on both cards in the estate — 5080 at 20.2 TFLOPS fp32, and 4090 (sm_89, running the sm_86 binaries) at 35.4: 

docker run --rm --gpus all pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime \
  python -c "import torch; a=torch.randn(4096,4096,device='cuda'); print((a@a).sum().item())"

Always finish acceptance with a real matmul rather than nvidia-smi. A failure here looks like a driver fault and is not one.

03 Restore access before you walk away

A reimage wipes authorized_keys for every account and regenerates the host keys. Both need attention or the node is console-only. 

# on the node, for each account that needs it
mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo '<your ed25519 public key>' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
# on your workstation, clear the old host key or SSH refuses to connect
ssh-keygen -R 10.31.96.247
If keys are installed but still rejected

sshd ignores authorized_keys when the home directory or .ssh is group- or world-writable — a common state on a fresh image. sudo journalctl -u ssh -n 20 names the reason directly rather than leaving you guessing at Permission denied (publickey).

04 Per-user setup

No root needed past this point. Run as the account that will use the node.

curl -fsSL https://raw.githubusercontent.com/lkk688/edgeAI/main/jetson/install_gputool.sh | bash
source ~/.bashrc

gputool device          # driver health, disk, conda, gputool — one screen
gputool profile         # the serving defaults this GPU gets
gputool install-conda
gputool setup-env py312 3.12
gputool install-ai      # chat + agent, no repo checkout needed

gputool device is the acceptance test: it reports kernel module state, DKMS registration and whether gcc-12 is present, which together are what predict the driver surviving the next kernel upgrade.

05 Two traps specific to this hardware

20 cores, 30 GB RAM, 2 GB swap

That ratio is the reason node 02 once had to be power-cycled. Anything that parallelises per core — a CUDA build, or vLLM's flashinfer JIT compiling attention kernels — spawns 20 compilers at 1–2 GB each, exhausts RAM, and the kernel OOM-killer takes sshd with it. The machine stays pingable and becomes unreachable.

gputool now caps this automatically (llama.cpp builds by free RAM, MAX_JOBS=4 for vLLM). Anything you run by hand needs the same restraint: 

make -j4                       # not -j$(nproc)
MAX_JOBS=4 pip install vllm    # flashinfer JIT respects this
Do not upgrade the kernel casually

DKMS rebuilds for every installed kernel, so each stale one is another chance for a build to fail and wedge the install. Clear them with sudo apt autoremove --purge, and re-run gputool device after any kernel change — a node whose module failed to rebuild looks completely normal until someone calls torch.cuda.is_available().
